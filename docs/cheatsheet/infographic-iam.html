Will IAM Allow It?

One flowchart decides every IAM question: which policies AWS checks, in what order, and which of them can grant access instead of only limiting it.

An explicit Deny always wins. With no Deny, a request needs an Allow, and every guardrail on the way must leave room for it.

Hide the answers, then tap each one to check yourself.

The evaluation order

AWS checks every request in this order. Anything not explicitly allowed is denied.

Next checkDeniedAllowed
Explicit deny always wins

No allow anywhere can override a Deny statement, whether it is in an SCP, a bucket policy or an identity policy.

Same account: one allow is enough

Either the identity-based policy or the resource-based policy can grant access, as long as nothing denies it.

Cross-account: both sides must allow

The caller’s identity policy in its own account and the resource-based policy in the other account must both allow the action.

Guardrails never grant

SCPs, RCPs, permissions boundaries and session policies only set a maximum. Something else must still allow the action.

Cross-account access, two ways

Control callRequest to the resource
Way 1 · Assume a role

Works with every service. While using the role, the caller has only the role’s permissions, not its own.

Way 2 · Resource-based policy

Only for services with resource-based policies. The caller keeps its own permissions, which helps when copying between its own bucket and the other account’s bucket.

Policy types

Identity-based policy

Can grant

Attaches toUsers, groups and roles

The everyday allow. Use managed policies for reuse, inline only for a strict one-to-one link.

Resource-based policy

Can grant

Attaches toS3 buckets, SQS queues, SNS topics, KMS keys, Lambda functions, Secrets Manager secrets

Names a Principal, so it grants cross-account access without switching roles.

Role trust policy

Can grant

Attaches toEvery IAM role

Says who may assume the role: an account, a service such as ec2.amazonaws.com, or a federated identity.

KMS key policy

Can grant

Attaches toEvery KMS key

Required. IAM policies count only when the key policy lets them. The default key policy does, through the account principal.

Service control policy (SCP)

Only limits

Attaches toOrganization root, OUs and member accounts

Sets the most that principals in member accounts can do, the root user included. It never affects the management account or service-linked roles.

Resource control policy (RCP)

Only limits

Attaches toOrganization root, OUs and member accounts

Sets the most that anyone can do to resources in member accounts, e.g. block access from outside the organization.

Permissions boundary

Only limits

Attaches toOne user or role

Caps what that identity can ever get. Use it to let developers create roles without escalating their own access.

Session policy

Only limits

Attaches toOne assumed-role or federated session

Passed with AssumeRole or federation to narrow that session below the role’s own permissions.
