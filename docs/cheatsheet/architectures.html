Architecture diagrams

The patterns the exam keeps coming back to, drawn as traffic paths. For each one, know where the single points of failure are, what the cheaper option is, and which look-alike service is the trap.

1. Classic multi-AZ VPC

Traffic paths

  1. Request: user → internet gateway → ALB (public subnets) → EC2 in a private app subnet → RDS primary.
  2. Outbound (patches, external APIs): EC2 → NAT gateway in its own AZ → internet gateway → internet. Nothing on the internet can start a connection to the instance.
  3. Failover: if AZ A fails, the ALB stops sending to it, Auto Scaling replaces capacity in AZ B, and RDS promotes the standby; the DNS name stays the same.

Exam points

  • A subnet is public only because its route table sends 0.0.0.0/0 to an internet gateway. Instances there also need a public IP; put the ALB there, not the app.
  • One NAT gateway per AZ, each private subnet routed to its own. A single shared NAT gateway is a single point of failure and adds cross-AZ data charges.
  • NAT gateways are managed and scale on their own; NAT instances need source/destination check disabled and are the outdated answer. For IPv6, use an egress-only internet gateway.
  • Security groups are stateful and can reference other groups; network ACLs are stateless and need the ephemeral return ports (1024–65535) opened.
  • RDS Multi-AZ standby is for availability only and serves no reads; read replicas are for scaling reads. Aurora replicas do both.

2. Private access to AWS services

Gateway endpoint or interface endpoint?

Gateway endpointInterface endpoint (PrivateLink)
ServicesS3 and DynamoDB onlyMost AWS services (SQS, KMS, STS, Secrets Manager, ECR, …), S3 too, and your own or partners' services
How traffic gets thereRoute table entry for the service's prefix listAn ENI with a private IP in each chosen subnet; private DNS points the service name at it
CostFreePer hour per AZ, plus per GB
Reachable from on-premises or a peered VPCNoYes, over Direct Connect, VPN or peering
Access controlEndpoint policy, plus aws:SourceVpce in the bucket policyEndpoint policy and a security group on the ENI

Exam points

  • "High NAT gateway charges" with heavy S3 or DynamoDB traffic → add a gateway endpoint; it is free and needs no application change.
  • On-premises servers reaching S3 privately over Direct Connect → an S3 interface endpoint; a gateway endpoint cannot be reached from outside the VPC.
  • "Only from this VPC" for a bucket → bucket policy deny unless aws:SourceVpce (or aws:SourceVpc) matches.
  • Interface endpoints live in subnets, so add one per AZ for high availability; gateway endpoints are a route target and are highly available by design.
  • Exposing your own service to other VPCs, even with overlapping CIDRs → an NLB behind a VPC endpoint service, consumed through interface endpoints.
