Networking foundations

1. Classic multi-AZ VPC

Traffic paths

  1. Request: user → internet gateway → ALB (public subnets) → EC2 in a private app subnet → RDS primary.
  2. Outbound (patches, external APIs): EC2 → NAT gateway in its own AZ → internet gateway → internet. Nothing on the internet can start a connection to the instance.
  3. Failover: if AZ A fails, the ALB stops sending to it, Auto Scaling replaces capacity in AZ B, and RDS promotes the standby; the DNS name stays the same.

Exam points

  • A subnet is public only because its route table sends 0.0.0.0/0 to an internet gateway. Instances there also need a public IP; put the ALB there, not the app.
  • One NAT gateway per AZ, each private subnet routed to its own. A single shared NAT gateway is a single point of failure and adds cross-AZ data charges.
  • NAT gateways are managed and scale on their own; NAT instances need source/destination check disabled and are the outdated answer. For IPv6, use an egress-only internet gateway.
  • Security groups are stateful and can reference other groups; network ACLs are stateless and need the ephemeral return ports (1024–65535) opened.
  • RDS Multi-AZ standby is for availability only and serves no reads; read replicas are for scaling reads. Aurora replicas do both.

2. Private access to AWS services

Gateway endpoint or interface endpoint?

Gateway endpointInterface endpoint (PrivateLink)
ServicesS3 and DynamoDB onlyMost AWS services (SQS, KMS, STS, Secrets Manager, ECR, …), S3 too, and your own or partners' services
How traffic gets thereRoute table entry for the service's prefix listAn ENI with a private IP in each chosen subnet; private DNS points the service name at it
CostFreePer hour per AZ, plus per GB
Reachable from on-premises or a peered VPCNoYes, over Direct Connect, VPN or peering
Access controlEndpoint policy, plus aws:SourceVpce in the bucket policyEndpoint policy and a security group on the ENI

Exam points

  • "High NAT gateway charges" with heavy S3 or DynamoDB traffic → add a gateway endpoint; it is free and needs no application change.
  • On-premises servers reaching S3 privately over Direct Connect → an S3 interface endpoint; a gateway endpoint cannot be reached from outside the VPC.
  • "Only from this VPC" for a bucket → bucket policy deny unless aws:SourceVpce (or aws:SourceVpc) matches.
  • Interface endpoints live in subnets, so add one per AZ for high availability; gateway endpoints are a route target and are highly available by design.
  • Exposing your own service to other VPCs, even with overlapping CIDRs → an NLB behind a VPC endpoint service, consumed through interface endpoints.

3. Hybrid connectivity

VPN or Direct Connect?

Site-to-Site VPNDirect Connect
Ready inMinutesWeeks (a physical cross-connect)
PathEncrypted IPsec over the internetPrivate dedicated link, not encrypted by default
BandwidthUp to 1.25 Gbps per tunnel, varies50 Mbps to 100 Gbps, consistent
Use it forQuick start, low volume, backupSteady large transfers, predictable latency

Exam points

  • "Consistent bandwidth" or "predictable latency" → Direct Connect; "quickly" or "cheaply" → Site-to-Site VPN.
  • Maximum resiliency: two Direct Connect connections at two different locations. Two links at one location do not survive a location outage.
  • Direct Connect plus a VPN as backup is the cost-effective middle ground. Encryption over Direct Connect: run an IPsec VPN over it, or MACsec on dedicated links.
  • One Direct Connect gateway reaches VPCs in any Region; with a Transit Gateway it scales to many VPCs through a single transit VIF.

4. Transit Gateway hub and spoke

Exam points

  • "Hundreds of VPCs", "simplify the mesh" or "transitive routing" → Transit Gateway. Two or three VPCs that only talk to each other → peering is cheaper (no hourly attachment charge).
  • Peering is not transitive: A↔B and B↔C does not give A↔C, and peered VPCs cannot have overlapping CIDRs.
  • Share one Transit Gateway with other accounts through AWS Resource Access Manager; separate route tables keep, for example, dev and prod apart.
  • Connect Regions with Transit Gateway peering; connect on-premises with a VPN attachment or a Direct Connect gateway.

5. PrivateLink for a SaaS service

Exam points

  • "Expose one service to many VPCs or accounts", "overlapping CIDRs", "no internet" → a VPC endpoint service (NLB, or GWLB for appliances) consumed through interface endpoints.
  • Peering or a Transit Gateway would join whole networks and fails with overlapping ranges; PrivateLink exposes a single service, one way.
  • The provider can require acceptance of each endpoint connection; consumers can add endpoint policies and security groups.
  • Third-party SaaS on AWS (and AWS services themselves) are reached the same way: an interface endpoint with private DNS.

6. Hybrid DNS with Route 53 Resolver

Exam points

  • On-premises servers must resolve a private hosted zone → Resolver inbound endpoint, and a conditional forwarder on the corporate DNS server pointing at its IPs.
  • Instances must resolve on-premises names → Resolver outbound endpoint plus a forwarding rule for that domain; share the rule with other VPCs and accounts through RAM.
  • Both endpoints are ENIs in your subnets; put them in at least two AZs.
  • A private hosted zone answers only inside the VPCs associated with it; a public hosted zone answers everyone.

Highly available web applications

7. Three-tier web application

How a request flows

  1. Route 53 answers with an alias to the CloudFront distribution (an alias, not a CNAME, works at the zone apex and is free).
  2. CloudFront serves /static/* from its cache or S3, and forwards /api/* to the ALB; WAF filters both.
  3. The ALB picks a healthy instance in any AZ; the Auto Scaling group keeps enough instances running.
  4. Instances read from ElastiCache first, write to the RDS primary, and send heavy reports to the read replica.

Exam points

  • Keep the web tier stateless: sessions in ElastiCache or DynamoDB, not on the instance, so scaling in loses nothing.
  • Multi-AZ standby = availability (automatic failover, no reads). Read replica = read scaling (asynchronous, can be promoted, can be cross-Region).
  • Lock the bucket to CloudFront with Origin Access Control; lock the ALB to CloudFront with its managed prefix list or a secret header.
  • Scale on ALB request count per target or CPU with target tracking; use scheduled or predictive scaling for known daily peaks.

8. Serverless web application

Exam points

  • "Least operational overhead" with a spiky or unpredictable load → this stack. Lambda runs at most 15 minutes; longer jobs go to Fargate or Step Functions.
  • API Gateway usage plans and API keys give per-client throttling and quotas; a Cognito authorizer rejects calls without a valid token before Lambda runs.
  • Cognito user pools sign users in (tokens); identity pools exchange a token for temporary AWS credentials, for example to upload straight to S3.
  • Absorb bursts without losing requests: API Gateway → SQS → Lambda. Cold starts: provisioned concurrency (or SnapStart for Java).

9. CloudFront or Global Accelerator

Which one?

CloudFrontGlobal Accelerator
ProtocolsHTTP and HTTPS (and WebSocket)Any TCP or UDP: games, VoIP, IoT, MQTT
CachingYes, that is the pointNo
AddressesA DNS name; IPs changeTwo static anycast IPs to allowlist
FailoverOrigin groups on error codesBetween Regions in seconds, no DNS caching
ExtrasSigned URLs and cookies, Lambda@Edge, CloudFront Functions, geo restrictionClient IP preservation, traffic dials per Region

Exam points

  • "Static IP addresses", "UDP", "non-HTTP" or "fast regional failover" → Global Accelerator. "Cache", "static content", "reduce origin load" → CloudFront.
  • Both use the AWS backbone and come with Shield Standard; both work in front of an ALB or NLB.
  • Slow uploads from far away to S3 → S3 Transfer Acceleration (it uses CloudFront edges), not a CloudFront distribution.

Decoupling and event-driven design

10. Queue-based load leveling

How it behaves

  1. A burst arrives: the web tier keeps answering because it only writes to the queue.
  2. A worker receives a message; it stays invisible for the visibility timeout. The worker deletes it once done.
  3. If a worker dies, the message reappears and another worker takes it. After maxReceiveCount failed attempts it moves to the dead-letter queue.
  4. Backlog per instance (messages ÷ workers) above the target adds workers; an empty queue scales them back in.

Exam points

  • Orders processed twice → raise the visibility timeout above the longest processing time. Poison messages retried forever → add a DLQ.
  • Strict order or exactly-once → FIFO queue (message group ID for parallel ordered streams); standard queues are at-least-once with best-effort order.
  • Long polling (WaitTimeSeconds up to 20) cuts empty receives and cost.
  • Scale on backlog per instance, not CPU: target = acceptable latency ÷ seconds per message.

11. Fan-out with SNS and SQS

Exam points

  • "Several independent systems must each process every event" and "a consumer may be offline for hours" → SNS → SQS per consumer. SNS alone would drop messages for an endpoint that is down.
  • A subscription filter policy sends only matching messages to a queue, so consumers do not filter in code.
  • Ordered fan-out → SNS FIFO topic to SQS FIFO queues.
  • The queue's access policy must allow the topic to send; with SSE-KMS, the key policy must let SNS use the key.

12. Event routing with EventBridge

Exam points

  • "Route by content", "SaaS events with no polling" or "react to AWS service events" → EventBridge rules. Plain fan-out of identical messages → SNS.
  • Archive and replay keeps events for a set time and re-sends them after a bug fix; SNS and SQS have no replay.
  • API destinations call external HTTPS APIs with built-in auth (OAuth, API key) and rate limits; EventBridge Scheduler runs cron or one-off schedules at scale.
  • Cross-account: a rule on one bus targets another account's bus; the receiving bus needs a resource policy.

13. Workflow orchestration with Step Functions

Exam points

  • "Multi-step process", "retries with backoff", "human approval", "visual audit trail", "no custom state code" → Step Functions. Chaining Lambdas or sleeping in code is the wrong answer.
  • Standard: up to 1 year, exactly-once, priced per transition, for business workflows. Express: up to 5 minutes, high volume, at-least-once, for streaming and IoT.
  • Callback pattern .waitForTaskToken pauses for a person or an external system; Distributed Map fans a big S3 dataset out to thousands of parallel runs.
  • Direct service integrations (DynamoDB, SQS, SNS, ECS, Glue…) let a step call a service with no Lambda in between.

Data and analytics

14. Streaming pipeline

Data Streams or Firehose?

Kinesis Data StreamsData Firehose
You manageShards (or on-demand mode), consumersNothing, fully managed
LatencyReal time (~70 ms to 200 ms)Near real time (buffers 0 to 900 s)
ReplayYes, within retentionNo
ConsumersYour code: Lambda, Flink, KCL appsDelivers to S3, Redshift, OpenSearch, HTTP endpoints
TransformsIn your consumerLambda transform, Parquet conversion

Exam points

  • "Replay", "several consumers", "ordering per key", "real time" → Data Streams. "Load into S3/Redshift/OpenSearch with no code" → Firehose.
  • Shard limits: 1 MB/s or 1,000 records/s in, 2 MB/s out shared; enhanced fan-out gives each consumer its own 2 MB/s per shard.
  • Order is kept per partition key (per shard); a hot key overloads one shard.
  • Real-time SQL or windowed aggregations on a stream → Managed Service for Apache Flink. Kafka compatibility → Amazon MSK.

15. Data lake on S3

Exam points

  • Athena is slow and expensive on raw JSON → convert to Parquet or ORC, compress, and partition by date; you pay per TB scanned.
  • "Schemas unknown", "catalog the data" → Glue crawler + Data Catalog. Serverless ETL → Glue jobs; big Spark/Hadoop clusters you tune → EMR.
  • Different teams may see different columns or rows of one table → Lake Formation grants, not separate copies or bucket policies.
  • Join warehouse tables with S3 data without loading it → Redshift Spectrum. Fast dashboards for many users → QuickSight with SPICE.

16. Event-driven S3 processing

Exam points

  • "Process each upload as it arrives" with variable volume → S3 event notification → Lambda. Polling the bucket on a schedule is the wrong answer.
  • Lambda stops at 15 minutes and 10 GB of memory; longer jobs → SQS + Batch, ECS on Fargate, or Step Functions.
  • Let clients upload directly with presigned URLs (or Cognito identity pool credentials); large files use multipart upload.
  • Fan the same event out to several targets or filter by content → send S3 events to EventBridge instead.

Databases

17. Read scaling and caching

Exam points

  • "Same queries thousands of times", "can tolerate slightly stale data" → ElastiCache (lazy loading / cache-aside with a TTL). Always-fresh cache → write-through.
  • "Reports slow down the database" → a read replica (asynchronous; the Multi-AZ standby of an instance deployment cannot serve reads).
  • "Too many connections" from Lambda, or faster failover with no app change → RDS Proxy.
  • DynamoDB with microsecond reads and no code rewrite → DAX, not ElastiCache. Redis vs Memcached: Redis for persistence, replication, sorted sets; Memcached for simple multi-threaded caching.

18. Multi-Region data

Exam points

  • Relational, "RPO of seconds, RTO of a minute", "low-latency reads in another Region" → Aurora Global Database (up to 5 secondary Regions, managed failover).
  • Key-value, "users in several Regions must write locally", "active-active" → DynamoDB global tables.
  • Cheaper but slower: RDS cross-Region read replica (promote manually) or cross-Region snapshot and backup copies.
  • Data residency: global tables replicate everything to every replica Region, so check where data is allowed to live.

Disaster recovery

19. Disaster recovery strategies

Choosing one

StrategyAlready in the DR RegionRecovery
Backup and restoreBackups onlyRestore data, deploy everything (hours)
Pilot lightReplicated data, AMIs, IaCLaunch the app tier, promote the DB (tens of minutes)
Warm standbyA small working copyScale it up, fail over DNS (minutes)
Multi-site active-activeFull productionDNS already spreads traffic (near zero)

Exam points

  • Read the RPO and RTO in the question, then choose the cheapest strategy that meets both.
  • RPO is how much data you can lose (replication frequency); RTO is how long you can be down (what must start).
  • Route 53 failover routing with health checks moves traffic; multi-site uses weighted or latency routing in both Regions.
  • Backups for ransomware: AWS Backup copies to another account with Vault Lock. Server replication for DR: AWS Elastic Disaster Recovery.

  • Work out transfer time: 1 Gbps moves about 10 TB a day. If the network cannot finish in time, ship it with Snowball.

  • Containers on Fargate or ECS that need shared persistent files → mount EFS.

Storage classes

StandardMillisecondsFrequently read data

Exam points

  • IA classes bill at least 30 days and 128 KB per object; Glacier tiers have 90 and 180-day minimums. Tiny or short-lived objects can cost more there.
  • "No one, not even root, can delete for 7 years" → Object Lock compliance mode. Governance mode can be bypassed with a special permission. A legal hold has no end date.
  • Replication requires versioning on both buckets and does not copy existing objects unless you run Batch Replication.
  • Clean up failed multipart uploads with an AbortIncompleteMultipartUpload lifecycle rule.

Security and multiple accounts

23. Multi-account landing zone

Exam points

  • "Set up many accounts with guardrails and a dashboard, with the least effort" → Control Tower (landing zone, Account Factory, preventive and detective controls).
  • SCPs cap what any principal in an account can do, root included; they grant nothing on their own and never restrict the management account.
  • Logs no one can tamper with → organization trail to a bucket in the log archive account, with Object Lock and log file validation.
  • Workforce access to many accounts → IAM Identity Center with permission sets, not IAM users per account. Customers of your app → Cognito.
  • Consolidated billing shares volume discounts, Reserved Instances and Savings Plans across the organization.

24. Cross-account access

Role or resource policy?

Assume a roleResource-based policy
Caller identityBecomes the role; gives up its own permissions meanwhileKeeps its own identity and permissions
Works forAny serviceServices with resource policies: S3, SQS, SNS, KMS, Lambda, ECR…
Third partiesRequire an external ID in the trust policyName their account or role in the policy

Exam points

  • A vendor needs access to your account → a role whose trust policy names the vendor's account and an external ID (confused-deputy protection). Never share access keys.
  • Cross-account S3 downloads fail with AccessDenied though the bucket policy allows them → the objects use SSE-KMS and the key policy is missing the caller.
  • Applications on EC2, Lambda or ECS get credentials from their own role (instance profile, execution role, task role), never stored keys.
  • Find resources shared outside your organization → IAM Access Analyzer.

25. Edge security and threat detection

Which service finds what?

ServiceLooks atFinds
GuardDutyCloudTrail, VPC Flow Logs, DNS logs (agentless)Compromised instances, crypto mining, odd API calls

Exam points

  • SQL injection and bad bots → WAF managed rules; HTTP floods from many IPs → WAF rate-based rule; large DDoS with expert help and cost protection → Shield Advanced.
  • Apply the same WAF rules to every account automatically → Firewall Manager (needs Organizations and Config).
  • Keep users from bypassing CloudFront → ALB security group allows only the CloudFront managed prefix list; S3 origins use Origin Access Control.
  • Automatic response to a finding → EventBridge rule → Lambda or a Systems Manager Automation runbook.
