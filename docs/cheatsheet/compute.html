Virtual servers

Amazon EC2

Virtual servers you fully control. The exam asks which family fits the workload and which purchasing option fits how steady it is.

Exam picks it when
You need full OS control or a custom kernel
Lift-and-shift of existing servers
Special hardware: GPU, huge RAM, local NVMe
Compute · RAM · Middle · Turbo burst · IOPS · Dense disk · P trains, Inf infers · X = eXtreme memory
Steady for years → RI / Savings Plan. Can be interrupted → Spot. Per-core license → Dedicated Host. Unknown or short → On-Demand.

Top traps
  1. Instance store is lost on stop or terminate. If data must survive, the answer is EBS, even when the question says "highest IOPS".
  2. Spot gives a 2-minute warning. Never pick it for databases or stateful work that can't be interrupted.
  3. A regional RI does not reserve capacity. Guaranteed capacity in one AZ = zonal RI or an On-Demand Capacity Reservation.
More details storage, purchasing specifics, other EC2 facts

Instance store vs EBS

Instance store Ephemeral

  • Local NVMe, highest IOPS
  • Survives reboot; lost on stop, terminate, host failure
  • Caches, scratch, replicated data

EBS Persistent

  • Network-attached; io2 Block Express up to 256K IOPS
  • Root volume deleted on terminate by default; extra volumes kept
  • Incremental snapshots in S3

Elasticity + self-healing

EC2 Auto Scaling

Keeps the right number of healthy instances across AZs in one Region. Most questions ask which scaling policy fits.

Exam picks it when
Replace unhealthy instances automatically
Add and remove instances as demand changes
Spread instances across AZs for high availability
Which scaling policy? Pick a scenario
Top traps
  1. App returns errors but instances aren't replaced? Turn on ELB health checks. By default the ASG only checks EC2 status.
  2. Memory and disk aren't native metrics. Install the CloudWatch agent to scale on them.
  3. An ASG can't span Regions. Use one ASG per Region behind Route 53.

Traffic distribution

Elastic Load Balancing

Spreads traffic across healthy targets in several AZs. The exam asks which type fits: ALB, NLB or GWLB.

Exam picks it when
Route by URL path, host or header → ALB
Static IPs, TCP/UDP, extreme performance → NLB
Third-party firewall or inspection appliances → GWLB
Which load balancer? Pick a scenario
ALB = Application (Layer 7, smart routing) · NLB = Network (Layer 4, fast, static IP) · GWLB = Gateway (Layer 3, appliances)
Top traps
  1. An ALB has no static IP. Need fixed IPs? Use an NLB with Elastic IPs, or put Global Accelerator in front of the ALB.
  2. Behind an ALB, the app sees the load balancer's IP. The client's IP is in the X-Forwarded-For header. An NLB keeps the source IP.
  3. AWS WAF attaches to an ALB, not an NLB. "Block SQL injection or XSS at the load balancer" → ALB + WAF.
More details cross-zone, sticky sessions, SNI, draining
Cross-zone load balancingALB: on by default, free. NLB and GWLB: off by default; inter-AZ data is charged when on.
Sticky sessionsALB uses cookies; NLB sticks by source IP. Can leave load uneven.
SNISeveral TLS certificates (from ACM) on one listener, one per domain. ALB and NLB.
Deregistration delay300 s by default (0–3600). Lets in-flight requests finish before a target leaves.
Health checksPer target group. Unhealthy targets stop getting traffic; an ASG using ELB checks replaces them.
SSL offloadingTerminate TLS at the load balancer so targets serve plain HTTP.
Global AcceleratorTwo static anycast IPs in front of ALB, NLB or EC2, with fast multi-Region failover.
Internal load balancersPrivate IPs only, for tiers inside the VPC.
Classic Load BalancerLegacy. Never the answer for a new design.
Serverless functions

AWS Lambda

Run code on events with no servers, paying per millisecond. Many questions really ask whether Lambda can't do the job, so learn the limits.

Exam picks it when
Short, event-driven work, under 15 minutes
Unpredictable traffic; pay only while code runs
"Least operational overhead", "no servers to manage"

Orange = know by heart. The rest: recognize them when you see them.

Reserved Free

Guarantees and caps how many copies of one function can run. Protects a database and stops one function starving others.

Provisioned Paid

Keeps environments pre-initialized, so there are no cold starts. For Java, SnapStart does this for free.

Reserved = reserved seats (a cap). Provisioned = pre-warmed engines (no cold start).

Synchronous

API Gateway, ALB, Function URL. The caller waits and retries itself.

Asynchronous

S3, SNS, EventBridge. Lambda retries twice, then DLQ or on-failure destination.

Poll-based

SQS, Kinesis, DynamoDB Streams. Lambda polls in batches; streams keep order per shard.
Top traps
  1. Longer than 15 minutes isn't Lambda. Use Fargate, AWS Batch, or split the work with Step Functions.
  2. A public subnet doesn't give Lambda internet. It never gets a public IP. Use a private subnet with a NAT gateway.
  3. Too many database connections? Put RDS Proxy between Lambda and RDS.
More details features, Lambda vs Fargate vs EC2

PaaS · no extra charge

Elastic Beanstalk

Upload code; Beanstalk builds the EC2 instances, Auto Scaling group and load balancer for you. The exam loves its deployment policies.

Exam picks it when
Developers deploy code without managing infrastructure
A traditional web app, and the team still wants EC2 access
Quick deploy with scaling and monitoring built in
Deployment policies · read the summary, press Play to see it happen
v1 (old) v2 (new) updating launching
Fast and cheap → safe: All at once → Rolling → Rolling + batch → Immutable / Traffic split → Blue/Green
Top traps
  1. RDS created inside the environment is deleted with it. For production, create RDS separately and connect to it.
  2. Blue/Green isn't a built-in policy. Clone the environment, deploy, then swap environment URLs (CNAME).
  3. "Infrastructure as code for any resource" is CloudFormation, not Beanstalk.

Your app code

Task role

Read S3, write DynamoDB: what the application does.
ECS / Fargate

Task execution role

Pull the image from ECR, write logs, fetch secrets.
EC2 host

Instance profile

For the ECS agent. Never app permissions.
Task role = what the task DOES. Execution role = what ECS needs to EXECUTE it.
Top traps
  1. Task role vs execution role. "Can't pull from ECR / write logs" → execution role. "App needs S3" → task role.
  2. Fargate has no GPU, privileged mode or host access. Those need the EC2 launch type.
  3. Shared persistent storage across tasks and AZs is EFS, not EBS or instance store.

Exam picks one of these when
"Thousands of queued batch jobs" → AWS Batch
"Least effort to run a web app from code or an image" → App Runner
Low latency in a city, on 5G, or on-premises → Local Zones / Wavelength / Outposts
← AWS data centersYour building →
Top traps
  1. Local Zones = near users in one city. Wavelength = inside 5G carrier networks. Outposts = in your own data center.
  2. App Runner vs Beanstalk. App Runner: containers or source code, zero infrastructure setup. Beanstalk: classic app platforms, with EC2 access.
  3. Lightsail is for simple, small workloads. Enterprise scaling, custom networking or complex architectures → EC2.

Numbers

Don't mix these up

It's NOT the answer when…

  • Lambda: over 15 min, needs a GPU, over 10 GB memory, or a long-lived connection
  • Instance store: data must survive stop or terminate
  • Spot: databases or stateful work that can't be interrupted
  • Public subnet for Lambda: no public IP, so use private subnet + NAT
  • Fargate: GPU, privileged containers, host access, custom AMI
  • ASG alone: scaling across Regions
  • Beanstalk: general infrastructure as code (CloudFormation)
  • Beanstalk-managed RDS: production data
  • Simple scaling: modern answer is target tracking or step
  • Instance profile for container permissions: use a task role
  • Regional RI when capacity must be guaranteed
  • ALB: a static IP is required (NLB or Global Accelerator)
  • NLB: WAF is required (WAF attaches to ALB)
