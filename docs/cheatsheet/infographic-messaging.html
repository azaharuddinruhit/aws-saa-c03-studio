Queues, Streams and DR

Five ways to pass messages between services, the SQS settings the exam asks about, and the four disaster recovery strategies from cheapest to fastest.

Ask who must receive each message: one worker means SQS, every subscriber means SNS, a routed event means EventBridge, and replay for many readers means Kinesis.

Hide the answers, then tap each one to check yourself.

Five ways to connect services

SQS

Queue

Each message is processed by one worker, then deleted. The queue absorbs spikes so the workers can run at their own pace.

SNS

Fan-out

Every subscriber gets its own copy. Put an SQS queue behind each subscriber that must not miss a message.

EventBridge

Event routing

Rules match event content and send it to targets. Takes events from AWS services, SaaS partners and schedules.

Kinesis Data Streams

Stream

Records stay in the stream, in order per shard, and every consumer reads all of them, at its own pace, and can replay.

Amazon Data Firehose

Delivery

Buffers incoming data and loads it into a destination with no code to write. Near real time, because it waits to fill a buffer.

SQS settings the exam asks about

Visibility timeout

Hides a message while a worker processes it. Set it longer than the processing time, or another worker picks the message up again.

Dead-letter queue

Receives messages that failed too many times, so one bad message does not block the queue.

Long polling

Waits for messages instead of returning empty, which cuts empty receives and cost.

Delay queue

Holds new messages back for a set time before workers can see them.

FIFO groups and deduplication

Message groups keep order per group, and deduplication drops repeats within a short window, for exactly-once processing.

Large payloads

Store the body in S3 and send a pointer, which the SQS Extended Client Library does for you.

Also in this space

Step Functions

Orchestrates steps with retries, branches, waits and human approval. The answer when the workflow itself must be managed.

Amazon MQ

Managed ActiveMQ and RabbitMQ. The answer when existing apps speak JMS, AMQP or MQTT and must not be rewritten.

Amazon MSK

Managed Apache Kafka, for teams already on Kafka.

The DR ladder

Each rung keeps more running in the recovery Region, so recovery is faster and the bill is higher.

RPO

How much data you can lose, measured as the time since the last good copy.

RTO

How long the service can be down before it is back.

Pick the cheapest that fits

Choose the lowest rung whose RTO and RPO meet the requirement. Anything higher costs more for no gain.

AWS Elastic Disaster Recovery

Replicates servers block by block into low-cost staging and launches them on failover, from on-premises or another Region.

AWS Backup

Central backup plans, with copies to another Region or account. Vault Lock makes them immutable.

Route 53 failover

Health checks move DNS to the standby Region. Application Recovery Controller adds readiness checks and manual routing switches.

Traps the exam sets

A standard SQS queue processes orders in sequence.

Standard queues can reorder and repeat. Use a FIFO queue.

One SQS queue delivers every order to three services.

Each message goes to one consumer. Fan out with SNS to a queue per service, or use EventBridge.

Use Kinesis Data Streams as a simple job queue.

For jobs that each need one worker, SQS is simpler and cheaper.

Firehose runs custom code on every record within a second.

Firehose buffers before delivery. Use Kinesis Data Streams with your own consumers.

Messages are processed twice, so raise the retention period.

The visibility timeout is shorter than the processing time. Raise the visibility timeout.

A message that always fails blocks the queue.

Set a dead-letter queue with a maximum receive count.

Pilot light serves full traffic the moment the Region fails.

Its app servers must start and scale first. Warm standby is already serving.

Multi-site active/active is the cheapest DR that works.

Backup and restore is cheapest. Pick the lowest rung that meets the RTO and RPO.
